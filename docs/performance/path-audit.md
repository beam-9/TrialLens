# M0 executed-path audit

Baseline commit: `031ff95daa553d874a8c2ef36ab7b18ec96e0e0f`; worktree was clean before M0. This audit records existing behavior, not optimization changes. All six handoff source documents exist under `docs/`; retained `apps/api/evaluation/final-results.json` and `workspace-browser-results.json` also exist. No repository `CONTEXT.md`, `AGENTS.md` or ADR files were found by the initial filename search.

## Click to displayed answer

1. `apps/web/app/page.tsx`, `ask()`: validates question and busy state, sets pending state, awaits `api.ask`. The composer remains pending while the single response is outstanding. After success it sets answer/history state and schedules focus/scroll through two animation frames; usage is refreshed separately without blocking answer display.
2. `apps/web/lib/api.ts`: serializes question, mode, source filter, source ID and previous answer ID to JSON; browser fetches the same-origin `/api/workspaces/{id}/ask` by default. It awaits response JSON. There is no token stream, polling or client-side model call.
3. `apps/web/app/api/[...path]/route.ts`: an asynchronous Node proxy forwards to the configured API base (default loopback port 8000), no caching. A 390-second abort signal and request-disconnect signal bound proxy fetch; route metadata permits 400 seconds. It forwards the response body. These bounds are not promises about an external host's hard runtime limits.
4. `apps/api/triallens/main.py`, synchronous `ask()` route: FastAPI runs this sync endpoint in its threadpool. It reads workspace, chunks, sources and extraction rows, then follows up to six prior answers. History must match workspace and exact source scope; filters apply to sources, chunks and extractions together. Each store read parses the entire JSON file. `retrieval_question` carries user question referents forward without treating assistant answers as evidence.
5. Workspace retrieval calls `Retriever.retrieve_conversation`: deterministic hashed features plus lexical/topic/intent scores. Broad questions diversify relevant sources before the eight-passage cap; mixed benefits/safety performs two retrieval/ranking operations and interleaves them. Document mode uses its own source-scoped retrieval/answer path. Extractive `AnswerService` builds a safe fallback first.
6. The route ranks unique source IDs from retrieved chunks and qualifying extraction citations, selects those source records, then invokes `ConversationService.generate`. Personal treatment and unresolved-comparison guards may return without model inference. Missing sources/configuration also return without inference.
7. Context construction in `conversation.py` performs standalone/combination-label scoping before selecting at most eight sources. A total 28,000-character text budget is divided across selected sources; at most four matched passages per source take priority, with remaining budget for at most 10,000 opening characters. Source titles/citation metadata, prompts, history and generated draft consume additional context. This character cap does not guarantee token fit. Local history is bounded to three turns and 2,000 answer characters each.
8. The process-wide generation lock is acquired **nonblocking after context construction** and covers both local calls, validation and local usage accounting. Busy requests return labeled excerpts rather than waiting for inference. This lock is not shared across API processes. Context/store/retrieval work still occurs for a busy response.
9. First blocking `httpx.post` sends the structured schema request to fixed `http://127.0.0.1:11434/api/chat` with `trust_env=False`. Second call is sequential: it appends the complete draft and revision instruction/current question, so the revision prompt is larger than the first. Both requests use `stream=False`, `think=False`, `temperature=0`, `num_ctx=16384`, `num_predict=1800`, `keep_alive=10m`, and an HTTPX timeout value of 180 seconds. HTTPX's scalar timeout applies to network inactivity/operation phases, not a strict end-to-end 180-second stopwatch. Requests require `done=True` and reject `done_reason=length`; actual model truncation must be measured separately.
10. Validation parses the JSON schema, normalizes only exactly known citation-format variants, checks allowed/exact markers and uncertainty-marker scope, rejects unsupported uncited claims unless phrased as abstention, and rejects 28-word verbatim spans. These are structural safeguards and cannot establish biomedical entailment. The same model performs revision, not independent clinical review. Successful local generation updates SQLite once at zero paid cost. HTTP, validation and usage failures preserve labeled fallback behavior; `finally` releases the generation lock on all guarded exits.
11. `JsonStore.save_answer` locks the entire mutation, reparses the JSON store, writes/fsyncs a complete temporary JSON snapshot and atomically replaces it. The route returns an `Answer`; FastAPI/Pydantic serializes it after the synchronous function returns. Browser JSON parsing and React paint follow. Server-route instrumentation alone cannot measure browser paint or all FastAPI/proxy serialization overhead; those boundaries must be reported honestly.

## Native runtime, unchanged

The observed service is `/opt/homebrew/bin/ollama serve`, a child of `apps/api/run.py`, not a Docker-hosted runtime. Client/server version: 0.32.14. Installed baseline: `qwen3.5:9b`, digest `6488c96fa5faab64bb65cbd30d4289e20e6130ef535a93ef9a49f42eda893ea7`, Q4_K_M, 9.7B. See `environment.json` for hardware and exact observations.

The existing launcher already starts its owned service with `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE=q8_0`, loopback host and cloud disabled. These settings were also observed in the current native service's startup log. The log reports `OLLAMA_MAX_LOADED_MODELS=0`; the application does not explicitly set it, so do not report a one-loaded-model configuration as already applied. If another service already exists, the launcher reuses it without setting those child-process variables. No runtime settings were changed for this audit.

Before baseline inference `ollama ps` was empty. GPU residency must therefore be captured once the model is actually loaded. Pre-load Activity Monitor was actually inspected: green memory-pressure graph, 16.00 GB physical, 13.25 GB used, 3.72 GB swap. Existing swap is not attributable to the upcoming inference; use system counter deltas, pressure and loaded-model observations together. These are system-wide measurements with other applications running, not isolated process allocation or proof of a memory leak.

## Measurement boundaries and risks

- Two model passes are necessarily serial, but their relative load/prompt/decode shares are unknown until measured. Do not assume revision dominates.
- Store reads/history traversal repeatedly parse the full store, and save rewrites the full store; profile rather than rewrite the architecture in M0.
- One 28K-character evidence budget omits tokenized schema/system/history/revision overhead. Advertised model context (262,144) differs from the request allocation (16,384). Actual prompt counts and runner truncation warnings are required for a safe later context experiment.
- The local path cannot silently fall back to a paid provider. A separate explicitly configured OpenAI branch exists and must remain uninvoked throughout the benchmark.
- Request disconnect can abort the proxy response while synchronous API inference continues; existing synchronous code has no cooperative cancellation hook. Telemetry should not claim it observes client disconnect unless measured at that boundary.
- Timeout/connection failure, validation rejection, busy admission, no-source fallback and valid conversational abstention are distinct outcomes; source excerpts are not successful model answers.

## Loaded and sustained observations

During the native baseline run, `ollama ps` actually reported `100% GPU`, context `16384`, size `5.7 GB`; `/api/ps` reported `size_vram=5662425741` and `size=5662425741` bytes. This confirms the loaded runner's residency report, not the fraction of elapsed time spent doing GPU work.

Activity Monitor was inspected again during sustained inference: its pressure chart was green, memory used approximately 15.06 GB, wired approximately 9.44 GB, compressed approximately 3.39 GB, swap approximately 5.88 GB. Kernel pressure samples concurrently reported level 2. These distinct observations are retained rather than replacing one with an inferred color/state.

Swap used increased from 3837.56 MiB before model loading to 5818.94 MiB in the first loaded sample. It subsequently fell to 5762.94 MiB, then grew to 6647.75 MiB over 120 seconds; the next sample 31 seconds later was 6648.25 MiB. The root agent was alerted to the sustained growth and subsequent near plateau. No level-4 pressure was observed in these samples. This does not isolate the model as the sole cause: other applications were running and measurements are system-wide. Per-sample counters and UTC timestamps are retained in `environment.json`; interpret any later memory stop condition using the complete benchmark trace.

The actual local virtualenv reports Python **3.9.6**, while `apps/api/pyproject.toml` declares **>=3.11**. M0 did not upgrade it; reproducibility on the supported runtime remains a risk to record alongside test results.

### Later growth and stop recommendation

The apparent near plateau did not persist. At 05:37:39Z an independent sample recorded 7668.25 MiB swap; at 05:38:09Z it recorded 7788.12 MiB (+119.87 MiB in 30 seconds). This is +3950.56 MiB versus pre-load and +1140 MiB over 149 seconds after the earlier near plateau. Swapout counters continued increasing; kernel pressure remained 2 and the loaded runner still reported 100% GPU, 16384 context. Runner RSS was 6,376,656 KiB in the later sample; the server process was 65,536 KiB (RSS excludes some shared/Metal allocation semantics and is not total unified-memory usage).

The auditor recommended that the root agent stop the loop conservatively rather than continue chasing the full fixture count under sustained swap growth on this 16 GB machine. This operational judgment applies the handoff's stop condition; it does not claim mathematically unbounded growth, critical level-4 pressure, a memory leak, or inference-only causality. The root agent owns safe interruption and the final benchmark completion status. Future profiling should retain this run and measure a quieter, explicitly documented desktop workload before declaring memory stability.

### Actual stop and cleanup

Root stopped the benchmark via SIGINT during request 16 following the memory recommendation. Fifteen of eighteen planned cases completed: one cold request, twelve warm two-pass requests (eleven model answers and one excerpt fallback), plus two deterministic guards. The interrupted request is not a completed latency sample. Three fixtures remain unrun or incomplete, so this is a partial minimum latency baseline and does not close the full M0 QA gate. No optimization milestone began.

After root restored the original unloaded state, the auditor independently confirmed at **05:40:42Z** that both `ollama ps` and `/api/ps` contained no loaded model. Kernel pressure returned to **1**, wired pages fell to **180836** (16 KiB pages, approximately 2.76 GiB), compressor pages to **87062**, and swap used was **7578.31 MiB**. Swap allocation can persist after unloading; it is not evidence that the runner remained resident. The Ollama service itself remains available. No additional inference was performed for cleanup verification.
